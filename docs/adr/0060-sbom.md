# 0060. An SBOM on the ci-accelerator image

Date: 2026-11-09

## Context

Releases sign the image and the charts (cosign) and attach a provenance
attestation to the image. A user's security team often also asks for a
software bill of materials: the packages the image contains, in a format
its tools read. The image is distroless with a static Go binary, so a
scanner already finds the Go modules in the binary; an SBOM is about what
the publisher states, not about new findings.

## Decision

- `scripts/build-image.sh` asks BuildKit for an SBOM attestation next to
  the provenance: SPDX, one per platform, made by
  `docker/buildkit-syft-scanner`, pinned by digest and followed by
  Renovate like every other image.
- The release workflow runs `scripts/check-sbom.sh` on the pushed image
  before it signs: each of linux/amd64 and linux/arm64 must carry an
  SPDX document with packages, read the way a user reads it
  (`docker buildx imagetools inspect --format '{{json .SBOM}}'`).
- No SBOM for the charts (they hold no software of their own) or for the
  third-party images the charts run (their publishers' to make).

## Consequences

- From 0.5.2 on every image has one; earlier images stay as they were.
- The SBOM generator is one more image a release pulls; a release fails
  when it cannot produce the SBOM, rather than publish an image without it.
